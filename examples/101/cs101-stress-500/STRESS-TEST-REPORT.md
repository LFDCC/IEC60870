# CS101 压力/性能测试报告

工具：`examples/101/cs101-stress-500`（Release，net8.0）

拓扑：N 个装置从站（**IEC 60870-5-101 平衡链路 over TCP 隧道**，端口 26000+i）
+ N 个主站一一对应独立链路。单进程同时跑 2N 个端点。

与 104 压测工具（`examples/104/cs104-stress-500`）**同口径**，便于横向对比：

| 维度 | 101（本工具） | 104（cs104-stress-500） |
|---|---|---|
| 每装置端口 | 26000+i | 25000+i |
| 自发速率 | `--spont` 4/s/装置 | 同 |
| 命令周期 | `--cmd-interval` 250 ms | 同 |
| 总召唤 | `--gi-interval` 10 s | 同 |
| 每报文测点 | `--points` 8 | 同 |

## 复现

```bash
dotnet run -c Release --project examples/101/cs101-stress-500 -- \
    --devices 500 --duration 60 --json results/metrics-500devices-v6.1.0.json
```

原始输出：`results/run-500devices-v6.1.0.log`

## 与 104 的对比（同一个 500 装置、同一台机器）

| 指标 | 101 | 104 |
|---|---|---|
| 合计 ASDU/s | 11,244 | 10,719 |
| 命令 RTT P99 | **76.6 ms** | **1.04 ms** |
| CPU 平均（整机占比） | 12.8 % | 4.8 % |
| 工作集 | 138 MB | 355 MB |
| 每装置内存 | 283 KB | 727 KB |

**两条关键结论**：

1. **101 的控制命令慢约 70 倍（P99 76 ms vs 1 ms），这是链路层模型决定的，不是缺陷。**
   104 有 APCI + k/w 窗口，可以连续发多帧、流水线往返；101 的 FT1.2 是
   「一帧一确认」（FCB 交替 + ACK），主站每发一帧必须等对端确认才能发下一帧，
   所以单次命令往返 = 一个完整链路层回合。
2. **101 的每装置内存反而只有 104 的 39 %**（283 KB vs 727 KB）：
   没有 k 缓冲、没有 APCI 适配器、没有 T1/T2/T3 定时器与重发表。

补充观察：命令 RTT 在 **20 装置与 500 装置下几乎相同**（均值 30.2 ms vs 35.5 ms），
说明这 ~30 ms 是**每条链路固定的单回合开销**（链路层回合 + 传输读超时粒度量级），
而不是 500 链路之间的相互竞争 —— 即 500 台不会让单条命令变慢。

## 适用性判断

- 若现场是「500 台 101 装置 + 秒级/百毫秒级遥控」，本结果直接可用；
- 若要求毫秒级控制响应，101 的链路层回合开销决定了做不到，应走 104；
- 若要求高吞吐遥测，101 也可以通过增大 `--points`（每帧多带测点）提升，
  但受 FT1.2 单帧 L 长度（1 字节，最大 255）限制，上限远低于 104。
