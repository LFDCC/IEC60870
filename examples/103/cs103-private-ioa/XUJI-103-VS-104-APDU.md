# 许继 103 网口报文：跟规约 PDF 差在哪

给不熟悉 103/104 的开发者看的版本。

## 先说结论（三句话）

1. **许继那份 103 规约 PDF 里，一个「网口」都没提**——它通篇只讲串口（RS-232/485）上的帧格式。
2. **但现场装置（2403 端口）跑的不是 PDF 里那套**，它借用了 104 的帧格式。
3. 所以：**照 PDF 写解析器，一条报文都收不对**。必须按抓包来。

---

## 一、先搞懂两个基本概念

### 什么是「帧」？

串口/TCP 上传来的是连续字节流，解析器得先知道「从哪到哪是一帧」。
这个「切分规则」就是帧格式。

### 两种切分方式

**103 用的是 FT1.2**——靠「重复长度 + 第二个 0x68 + 校验和 + 0x16 结束符」来定界：

```
68 0A 0A 68 53 01 [ASDU...] 5C 16
│  │  │  │  │  └─ 地址
│  │  │  │  └──── 控制域
│  │  │  └─────── 再来一个 68（防误判）
│  │  └────────── 长度再写一遍
│  └───────────── 长度
└──────────────── 起始符
                                        ↑  ↑
                                      校验和 结束符
```

同一份长度写了两遍、末尾还有算术校验和与固定结束符——这是为**串口**设计的，
因为串口会丢字节、会串入噪声，必须多重自校验。

**104 用的是 APCI**——只靠「长度」定界，什么都不多写：

```
68 0E 00 00 00 00 [ASDU...]
│  │  └──────────┴─ 控制域 4 字节（发送/接收序号）
│  └──────────────── 长度
└─────────────────── 起始符
```

没有校验和、没有结束符、长度只写一次。这是为 **TCP** 设计的——
TCP 本身保证不丢不重不乱序，不需要应用层再校验一遍。

> 两套都以 `0x68` 开头，但**第二个字节之后完全不同**。这是最容易看走眼的地方。

---

## 二、许继现场是怎么做的

现场装置（许继 2005 年的保护装置）在网口上做了这么一件事：

> **报文用 104 的壳，内容还是 103 的。**

打个比方：

- **103** = 一套中文信件（内容是中文，格式是「信封 + 正文 + 签名 + 封口」）
- **104** = 一套英文快递单（内容是英文，格式是「单号 + 内容」）
- **许继做的事** = 拿中文信件的内容，装进英文快递单的格式里

结果就是：**拆信封的规则变了，但里面的内容还是中文。**

---

## 三、具体变了什么

### 变化 1：帧头换了一套

| | 103（规约 PDF） | 许继网口（现场） |
|---|---|---|
| 起始 | `68 L L 68` | `68 L` |
| 长度 | 写两遍 | 写一遍 |
| 控制域 | 1 字节（帧计数、功能码） | 4 字节（发送/接收序号） |
| 地址 | 帧里有 1 字节地址 | 帧里**没有**地址 |
| 校验和 | 有 | **没有** |
| 结束符 `0x16` | 有 | **没有** |

### 同一帧调定值请求，两种长相

```
PDF 版:  68 0A 0A 68 53 01 | 3D 81 14 01 B2 64 1F 00 | 5C 16
现场版:  68 0E 00 00 00 00 | 3D 81 14 00 01 01 B2 64 1F 00
         └── 帧头 ────────┘ └──────── 内容（ASDU）────────┘
```

注意：**`0E` 就是长度**。现场版总长 = `2 + 0x0E` = 16 字节，一分不差。
PDF 版总长 = `0x0A + 6` = 16 字节，也刚好 16——**同样长度，但长度域的含义完全不同**。

### 变化 2：内容里的「头部」多长了 2 字节

ASDU 开头的几个字节，记录着「这报文是什么、给谁、干什么」。两边字段一样，
但**其中两个字段各宽了 1 字节**：

```
PDF 版:  TI(1) VSQ(1) COT(1) CA(1)   FUN(1) INF(1)  = 6 字节
现场版:  TI(1) VSQ(1) COT(2) CA(2)   FUN(1) INF(1)  = 8 字节
                          ↑    ↑
                       各宽 1 字节
```

| 字段 | 干什么的 | 为什么变宽 |
|---|---|---|
| TI | 报文类型（61 = 定值） | 没变 |
| VSQ | 带了几个数据 | 没变 |
| **COT** | 传送原因（20 = 命令确认） | 104 规定 2 字节，第二个字节是「源发地址」 |
| **CA** | 给哪台装置 | 104 规定 2 字节，高字节=装置地址、低字节=扇区 |
| FUN | 功能类型（178 = 线路保护） | 没变 |
| INF | 信息序号（100 = 调定值） | 没变 |

**后果很严重**：如果按 PDF 的 6 字节头去解现场报文，
后面所有字段都会**错位 2 个字节**——FUN 会读成 1、INF 读成 1，完全对不上号。

### 变化 3：COT 的位含义不一样

COT 一个字节里有「原因值」和「否定标志」，两边把标志位放在不同位置：

| 位 | 103 | 104 |
|---|---|---|
| bit7 | **否定标志** | 试验标志 |
| bit6 | 原因值的一部分 | **否定标志** |
| bit5-0 | 原因值 | 原因值 |

**后果**：装置若回「拒绝」（104 编码 `0x55`），按 103 的规则解会读成
「原因 85、不是否定」——**把失败当成成功**。这是实际会踩的坑。

### 变化 4：装置会主动推数据了

这是最容易让代码跑不通的一点。

| | 103（规约） | 许继网口（现场） |
|---|---|---|
| 谁先说话 | 主站问，装置答 | 主站问，装置答 |
| 但数据怎么拿 | 装置放进「队列」，主站**再发一次召唤**才取得到 | 装置**收到就立刻回**，没有召唤这一步 |
| 代码怎么写 | `await RequestClass1Async(...)` 去拉 | 订阅 `AsduReceived` 事件等它推 |

> 103 的模型像「去邮局取件」：邮件到了你得自己再去一趟。
> 现场这套像「快递上门」：直接送到你手上。

所以定值读写的代码必须**订阅事件**，不能再用轮询召唤。

## 四、代码里的落点

| 内容 | 在哪 |
|---|---|
| 标准 103（FT1.2）实现 | 库 `IEC60870.CS103`（默认） |

库本身不含许继代码——许继这套属于**厂商私有**，通过接口注入：

```csharp
var options = new Iec103Options()
    .UseLinkParameters(l => l.FramingCodec = new XujiApduCodec());
```

## 五、一句话总结

> **许继网口 103 = 104 的帧格式 + 103 的报文内容。**
>
> 拆帧按 104，解内容按 103，但内容头部有 2 个字段变宽了。

## 六、按 PDF 实现会怎样（实测）

把现场报文的某个真实帧喂给按 PDF 标准实现的 FT1.2 分帧器：

```
输入: 68 0E 00 00 00 00 3D 81 14 00 01 01 B2 64 1F 00
结果: 切出 0 帧
报错: 可变帧头不一致（L1/L2 或第二启动字符错）
```

原因就是第 2、3 字节：PDF 要求 `0E 0E`（长度写两遍），现场是 `0E 00`。
第 4 字节 PDF 要求是第二个 `68`，现场是 `00`。

**从第 2 个字节开始就对不上了。**
